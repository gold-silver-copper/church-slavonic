# Expand Old Church Slavonic verb morphology with attested-corpus evaluation

Work in the existing `church-slavonic` Rust workspace. Expand its verb support from
the conservative v0.1 implementation into a linguistically specified, testable verb
engine. The change must be backed by both dictionary-paradigm evaluation and
independent tests against forms that occur in real Old Church Slavonic texts.

This task is about **Old Church Slavonic** (`cu`), not a later Russian, Serbian,
Bulgarian, Croatian, or other recension of Church Slavonic. Preserve manuscript and
editorial variation as evidence; do not silently normalize it into a later standard.

The governing principle is still honesty: an explicit `UnsupportedCell`,
`MissingLexicalMetadata`, or ambiguity result is better than an attractive invented
form. Expand coverage only where a rule, its inputs, and its validation target are
independently specified.

---

## 1. Read the current implementation before changing it

At minimum, inspect:

- `docs/MORPHOLOGY_SPEC.md`, `docs/ORTHOGRAPHY.md`, `docs/DATA_PIPELINE.md`,
  `docs/ARCHITECTURE.md`, and `docs/GUARDS.md`;
- `crates/old-church-slavonic-core/src/{grammar,verb,adjective,result,trace}.rs`;
- the public verb APIs and dictionary fallback in
  `crates/old-church-slavonic/src/`;
- verb parsing and rejection logic in
  `crates/old-church-slavonic-extractor/src/extract.rs`;
- the accuracy and optional UD evaluation paths in `crates/xtask/src/main.rs`;
- the current extraction and accuracy reports; and
- all verb, public-API, extractor-fixture, registry, and no-panic tests.

Record the starting metrics by regenerating the reports rather than copying old
numbers. At the time this prompt was written, the committed extraction report kept
3,945 finite cells, 6,408 l-participle cells, 2,760 other verb cells, and 369
participle citation cells. It rejected 153,310 declined-participle rows as not safely
attributed and 17,912 verb rows carrying `error-unrecognized-form`. Those are audit
signals, not quotas and not permission to re-admit malformed data.

The current core productively handles:

- presents for explicit IA1, IA2, II1, II2, and II3 lexemes with a supplied present
  stem;
- validated infinitives;
- the regular `-ти -> -тъ` supine component; and
- l-participles from an explicitly supplied aorist stem.

It does not yet productively derive imperfects, aorists, imperatives, or participial
stems. Exact dictionary cells may already expose some of those categories. Preserve
the table-first, rule-fallback contract while improving the core.

## 2. Establish source authority before implementing rules

Update `docs/MORPHOLOGY_SPEC.md` before, or in the same commit as, each rule. Every
productive rule must have a stable rule ID, an explicit input contract, examples,
known exceptions, and a citation to a grammatical source.

Use this separation of authority:

1. **Grammar sources define productive morphology.** Start with the University of
   Texas *Old Church Slavonic Online* grammar, which separately describes the
   imperfect, asigmatic/sigmatic/new aorists, l-participle, conjugation classes,
   imperatives, participles, passive voice, infinitive/supine, and verbal aspect:
   <https://lrc.la.utexas.edu/eieol_toc/ocsol>.
2. **Pinned English Wiktionary/Kaikki tables define the versioned dictionary target.**
   They are useful for full-paradigm comparison and lexical variants, but agreement
   with a table generated by the same template is not independent linguistic proof.
3. **Attested corpora define real-world surface evidence.** They are sparse samples,
   not complete paradigms. A form's absence from a corpus is never evidence that it
   is ungrammatical.

Audit the verb descriptions and the actual pinned template revisions. Do not infer a
rule merely by reverse engineering the current Kaikki output. If two grammatical
sources disagree, document the disagreement, return structured variants when both
are defensible, or leave the disputed prediction unsupported.

### Corpus sources

Support reproducible evaluation with these sources, subject to their licenses:

- **UD Old Church Slavonic PROIEL**:
  <https://universaldependencies.org/treebanks/cu_proiel/index.html>. It contains
  canonical OCS from PROIEL and TOROT, with manuscript text, lemmas, and manually
  based morphological annotations converted to UD. Pin an exact UD release or git
  commit. Its license is CC BY-NC-SA 4.0.
- **Original Syntacticus/PROIEL/TOROT data**:
  <https://github.com/syntacticus/syntacticus-treebank-data>. Inspect the native
  morphology when the UD conversion has discarded a distinction needed by the
  inflector. Pin an exact release or commit and document the tag mapping. This data
  is also noncommercial/share-alike; keep it external.
- **Corpus Cyrillo-Methodianum Helsingiense (CCMH)**:
  <http://urn.fi/urn:nbn:fi:lb-20140730106>. The University of Helsinki catalogue
  describes seven OCS texts with transliterations and structured XML under CC BY
  4.0. Audit the downloaded files, encoding documentation, and file-level license
  before using or redistributing any sample.

Do not download live, floating data during ordinary `cargo test`. Add an explicit
maintainer command that consumes local corpus paths and validates pinned hashes.

### Licensing boundary

- Never compile UD, PROIEL, TOROT, or Syntacticus text into either runtime crate.
- Do not commit CC BY-NC-SA corpus text, derived token listings, or mismatch excerpts.
  Keep detailed local reports gitignored; commit only aggregate metrics that do not
  reproduce the source.
- A small CCMH-derived regression fixture may be committed only after verifying that
  the exact distributed file is covered by CC BY 4.0. Include source file, stable
  identifier, version/hash, passage identifiers, attribution, license, and the
  transformation applied.
- If redistribution remains unclear, commit synthetic mapper fixtures plus corpus
  IDs and expected aggregate counts, not the corpus text.
- Keep all corpus attribution and evaluation instructions current in
  `ATTRIBUTION.md` and `docs/DATA_PIPELINE.md`.

## 3. Build a verb-system model, not a suffix collection

Before adding endings, write a short design section explaining the independent
dimensions of an OCS verb. Do not make `VerbClass` carry unrelated aorist,
imperative, participial, and aspect behavior.

Evolve `VerbLexeme` and related enums so that callers can supply the principal parts
or formation choices actually required by a rule. The precise Rust names are a
design decision, but the model should be capable of representing at least:

- infinitive/citation form;
- present class and present stem;
- an explicit present allomorph where the first-singular or another seam cannot be
  safely obtained from the default stem;
- infinitive or past-system stem when distinct;
- aorist stem and aorist formation type;
- imperfect base or a documented derivation policy;
- imperative base or allomorph;
- stems needed by each productive participle formation;
- lexical aspect as metadata, without confusing aspect with past-tense formation;
  and
- explicit irregular or suppletive overrides.

For example, a separate formation dimension might distinguish asigmatic, sigmatic,
and new aorists. This is illustrative, not a demand for those exact enum names.
Prefer typed fields and validated constructors over magic strings or flags.

Do not derive every principal part from the infinitive. Use a deterministic rule
only where the morphology spec demonstrates that the derivation is valid for the
declared class. Otherwise require metadata and report precisely which field is
missing. Extend `MetadataField` and traces accordingly.

Classify root and irregular verbs explicitly. Add table or lexical overrides for
well-attested irregular paradigms only after auditing them; do not force verbs such
as `бꙑти`, `дати`, `ѣсти`, `вѣдѣти`, `хотѣти`, or motion verbs through a productive
class merely to increase coverage.

## 4. Required productive capabilities

Implement in small, independently reviewable slices. A later slice may stay
unsupported if the grammatical or data audit cannot justify it, but the completed
work must visibly improve useful verb coverage.

### 4.1 Present-system corrections

- Preserve all currently supported present cells and variant ordering.
- Replace over-broad automatic consonant mutation with class/allomorph logic backed
  by the morphology specification.
- Evaluate every person and singular/dual/plural cell separately by class.
- Never use the target cell itself to infer the stem being evaluated.

### 4.2 Imperfect

- Model the productive imperfect base and any class-dependent stem formation.
- Generate only historically valid person-number cells, including dual.
- Specify orthographic and contraction variants. Return multiple variants only when
  their status is documented; keep deterministic ordering.
- Keep lexical exceptions and suppletive forms table-backed or explicitly
  overridden.

### 4.3 Aorist system

- Represent the supported aorist formations independently from present class.
- Implement asigmatic, sigmatic, and new-aorist behavior only to the extent justified
  by the cited grammar and audited paradigms.
- Make alternation, loss, length, palatalization, and stem-selection seams explicit
  and traceable.
- Do not pick an aorist formation from lexical aspect. Perfective/imperfective is not
  a substitute for formation metadata.
- When a lexeme permits multiple attested formations, expose structured variants
  with provenance instead of selecting one silently.

### 4.4 Imperative

- Add a productive imperative API with a typed cell.
- Encode only attested person-number combinations. Do not expose a meaningless full
  person-by-number Cartesian product just because finite verbs have one.
- Specify how imperative stems relate to present stems and where an allomorph or
  lexical override is required.
- Reject unsupported first- or third-person analyses unless the grammatical source
  explicitly treats them as morphological imperative forms.

### 4.5 Participles

Support stem formation and full agreement as separate stages for:

- present active;
- present passive;
- past active; and
- past passive participles.

Keep the existing l-participle type separate. Once a participial adjective stem is
known, reuse the existing adjective agreement resolver for case, number, gender,
animacy, and simple/compound form where applicable. There must be one owner for
adjectival endings, not a copied participle declension table.

The API must distinguish a participle citation from a declined participle. Preserve
voice, tense/relative-time category, agreement features, and variant/form type in a
typed cell. Do not classify a declined source row solely from an ambiguous flattened
tag list.

Do not generate analytic perfect, pluperfect, future, conditional, passive, or
reflexive phrases in the word inflector. In particular, `сѧ` is a separate token,
not an ending to concatenate blindly. Phrase morphology can be a later layer.

## 5. Repair source extraction before claiming new table coverage

The current Wiktextract rows can flatten table structure, attach a spurious
`l-participle` tag, and mark many valid-looking cells as
`error-unrecognized-form`. Do not solve this by weakening rejection guards.

Audit a stratified sample covering every verb template/class and each proposed
category. Compare:

- raw Kaikki/Wiktextract JSON;
- the corresponding pinned Wiktionary page/template invocation and revision;
- the rendered cell position and headings; and
- the extractor's proposed typed feature key.

If the flattened rows do not preserve enough information, parse a more authoritative
versioned input such as pinned Wiktionary template invocations or a deliberately
constrained positional block. Fixture-test each supported block shape and reject an
unknown shape atomically. Never assign one ambiguous row to many cells just to make
the counts rise.

For every accepted form retain enough provenance to reproduce the decision:

- source snapshot and hash;
- lemma/page identity;
- template and revision where available;
- raw form, raw ordered tags/headings, and normalized feature key;
- parser/mapping version; and
- whether the form is a source table cell, a corpus token, an override, or a rule
  prediction.

Generate before/after acceptance and rejection counts by category and reason. Review
large changes with concrete witnesses. Keep the extraction deterministic and atomic;
an invalid source must not partially replace committed generated data.

## 6. Add real-world corpus tests as a first-class evaluator

Extend or replace the current optional UD path with a command similar to:

```text
cargo xtask accuracy-corpus \
  --ud /path/to/UD_Old_Church_Slavonic-PROIEL \
  --syntacticus /path/to/syntacticus-treebank-data \
  --ccmh /path/to/ccmh
```

Individual inputs may be optional, but the command must identify exactly which
corpus, release/commit, files, hashes, and mapper version produced a report. Store
the expected pins in a reviewable manifest such as `data/evaluation-sources.toml`.
Fail on a hash or schema mismatch unless the maintainer explicitly runs a refresh
workflow.

### 6.1 Publish a feature-compatibility matrix

Document which corpus bundles can be mapped without loss. For UD OCS PROIEL, the
safe direct mappings include:

- `VerbForm=Fin`, `Tense=Pres`, `Person`, and `Number` -> present finite cell;
- `Mood=Imp`, `Person`, and `Number` -> imperative cell;
- `VerbForm=Inf` -> infinitive;
- `VerbForm=Sup` -> supine;
- `VerbForm=PartRes` plus gender/number -> l-participle; and
- `VerbForm=Part` plus tense, voice, case, number, gender, and variant -> a declined
  participle only when every required value has an explicit compatible mapping.

**Do not map UD `Tense=Past` finite verbs to aorist or imperfect.** The UD conversion
does not retain that distinction, and UD `Aspect=Perf|Imp` is lexical aspect rather
than aorist/imperfect identity. Mark those tokens as `incompatible-past-subtype`.
Evaluate aorists and imperfects only when the original native annotation retains the
distinction or when a small oracle has been manually audited against the manuscript
and independently reviewed.

Reject partial or contradictory bundles with counted reasons. Never let a mapper
guess missing person, number, voice, participle kind, or variant.

### 6.2 Separate three evaluation questions

Report these independently:

1. **Facade attested-token recall:** with committed dictionary tables and overrides,
   does the public API return the attested surface variant for a known lemma/cell?
2. **Core generalization with declared principal parts:** after supplying only
   permitted lexical metadata, and forbidding the evaluated table cell, can the rule
   engine produce the attested form?
3. **True OOV behavior:** on a lemma-disjoint holdout, can the engine operate from
   metadata that could be known without observing any target cell? State whether
   that metadata came from a dictionary principal part, another corpus token, or a
   manually curated lexeme record.

If a source token was used to infer a stem or formation, exclude that token and every
equivalent target cell from the score. Label any evaluation using gold metadata as
an oracle-metadata result, not end-to-end accuracy.

### 6.3 Prevent leakage

- Keep a fixed development partition and an untouched final partition.
- Group by normalized lemma so forms of one lexeme cannot occur on both sides of an
  OOV score.
- Also report by manuscript/document. Add a document-held-out view so orthographic
  behavior is not tuned on the same witness being evaluated.
- Freeze the partition function, seed/hash algorithm, exclusions, and corpus pins in
  version control before tuning rules.
- Never choose an override after seeing a final-holdout mismatch without moving that
  lemma into development and resetting the final baseline transparently.

The official UD train/dev/test split may still be reported for comparability, but it
is not automatically lemma-disjoint and therefore is not by itself an OOV test.

### 6.4 Orthography-aware scoring

Manuscript corpora contain case variation, abbreviations, titla, punctuation,
editorial brackets, lacunae, and spelling variants. Report at least:

- **diplomatic exact:** predicted surface equals the corpus token byte-for-byte;
- **project lookup exact:** only the already documented lookup normalization, such as
  Unicode normalization and case policy, is applied; and
- **morphology-normalized diagnostic:** an optional, separately documented fold for
  editorial or orthographic variants.

The diplomatic and project-lookup scores are primary. Never use a lossy fold to
inflate the headline result. Each normalizer must expose a trace and have tests
proving that it does not erase a morphological contrast.

Score top-1 and any-returned-variant separately. Variant order remains part of the
API contract.

### 6.5 Required denominators and slices

For every run report:

- all tokens and verb/AUX tokens seen;
- tokens with a compatible morphological bundle;
- tokens matched to an unambiguous project lexeme;
- tokens with sufficient lexical metadata;
- tokens for which a prediction was attempted;
- correct top-1 and correct-any-variant counts; and
- every skipped or rejected token by exact reason.

Report both coverage and conditional accuracy. Include micro and macro results by:

- manuscript/document;
- lemma and lemma frequency band;
- verb class and aorist formation where known;
- category: present, imperfect, aorist, imperative, infinitive, supine,
  l-participle, and each participle kind;
- complete morphological cell; and
- table-backed, override-backed, and productive-rule paths.

For local debugging, emit mismatch rows with corpus sentence/token ID, manuscript,
lemma, feature bundle, attested form, predictions, normalization trace, rule trace,
and skip/error reason. Keep non-redistributable details out of git.

An attested corpus is observational evidence. Do not score unattested generated cells
as wrong, infer paradigm completeness from token frequency, or compare a citation
form with an inflected token.

## 7. Keep a separate dictionary-paradigm/OOV evaluation

Extend the existing deterministic Kaikki/Wiktionary accuracy command for each newly
supported category. This evaluates paradigm coverage, not real-world frequency.

- Hold out the target cell and all exact duplicates before deriving metadata.
- Do not obtain an imperfect, aorist, imperative, or participial stem from the cell
  being predicted.
- Partition by lemma with the existing stable hash discipline, and freeze a final
  holdout before implementing a rule.
- Report class/formation/category/cell coverage and conditional exact accuracy.
- Separate failure causes: unknown class, missing principal part, unsupported
  formation, invalid source shape, rule mismatch, and orthographic-only mismatch.
- Compare all source variants structurally; do not concatenate variants into a
  delimiter string.

Keep the corpus evaluation and dictionary evaluation in different report sections.
Neither number may be presented as the other.

## 8. API and architecture requirements

- Keep `old-church-slavonic-core` deterministic, I/O-free, and independent of the
  generated dictionary.
- Keep the public crate table-first. A source cell wins; an override is explicit;
  productive fallback runs only with sufficient typed metadata.
- Preserve structured variants, provenance, stable rule IDs, and derivation traces.
- Return distinct errors for unsupported cell, missing lexical metadata, invalid
  input, ambiguous lexeme, and source-data failure where applicable.
- Avoid global mutable state, runtime network access, `unsafe`, and hidden
  normalization.
- Do not add a second implementation of morphology inside the evaluator. Production,
  dictionary OOV evaluation, and corpus evaluation must call the same public/core
  generation path.
- Keep generated registries deterministic and reviewable. Update fingerprints and
  semantic guards through the established pipeline.

Backwards compatibility is not a constraint. Prefer a coherent typed API over
preserving an insufficient v0.1 struct, but migrate every internal caller, example,
fixture, and test in the same change.

## 9. Tests required

Add or extend:

1. **Rule unit tests** for every ending, stem seam, alternation, formation, number,
   person, voice, and supported variant.
2. **Whole-paradigm goldens** for multiple regular verbs per class/formation and
   explicit irregulars. Goldens must cite their source.
3. **Boundary tests** showing where metadata is required and where a superficially
   similar lemma is rejected.
4. **Metamorphic tests** for invariants such as complete supported cell coverage,
   shared participle/adjective agreement, deterministic variant ordering, and
   consistent prefix handling where linguistically valid.
5. **Extractor fixtures** for every admitted raw source shape, including malformed,
   reordered, duplicated, missing-heading, and `error-unrecognized-form` cases.
6. **Corpus-mapper tests** for compatible, incomplete, contradictory, and lossy UD
   or native bundles. Include the `Tense=Past` non-mapping regression.
7. **Licensed real-data regression tests** if a redistributable CCMH fixture is
   verified; otherwise use synthetic schema fixtures and a repeatable local corpus
   integration test.
8. **Hostile-input/no-panic tests** for empty strings, combining marks, mixed
   scripts, editorial punctuation, oversized input, invalid cells, and adversarial
   Unicode.
9. **Public API and registry tests** proving exact table precedence, rule fallback,
   provenance, aliases, homograph handling, and generated-data synchronization.
10. **Regression accounting** that lists forms fixed and forms broken by every
    morphology slice. Review every break; do not hide it in an aggregate gain.

No ordinary test may require network access or the locally installed noncommercial
corpora.

## 10. Implementation order

Use this order so evaluation exists before it can be optimized:

1. Audit current verb source shapes and grammar; write the feature compatibility
   matrix and source/license manifest.
2. Implement the pinned optional corpus loader and take a baseline with the existing
   engine.
3. Redesign the principal-part/formation model and migrate callers.
4. Correct present allomorph handling.
5. Implement and evaluate the imperative.
6. Implement and evaluate the imperfect.
7. Implement and evaluate aorist formations one at a time.
8. Implement participial stems and reuse adjective agreement.
9. Re-admit source-table rows only through validated extraction mappings.
10. Regenerate all reports, run the complete verification suite, and review the full
    diff independently.

For each morphology slice:

- freeze the evaluation set first;
- add the morphology-spec rule and tests;
- implement through the production path;
- run targeted unit/golden tests;
- run dictionary OOV evaluation;
- run corpus evaluation on development data;
- inspect fixed and broken witnesses;
- run the untouched final evaluation once the design is stable; and
- record residual unsupported classes and why they remain unsupported.

## 11. Acceptance criteria

The task is complete only when:

- imperfect and imperative plus at least one independently specified aorist
  formation have productive typed APIs; if the source audit cannot support one of
  these safely, report the task as incomplete rather than weakening this gate;
- productive present-active, present-passive, past-active, and past-passive
  participle paths include both stem formation and declined agreement for at least
  one source-cited regular pattern each, with other classes rejected explicitly;
- every rule has a morphology-spec entry, stable rule ID, trace, tests, and an
  explicit metadata contract;
- dictionary cells still take precedence and existing supported verb categories do
  not regress without a reviewed linguistic reason;
- corpus pins, hashes, licenses, feature mappings, leakage controls, and denominators
  are documented and machine-checked;
- the real-world report separates coverage from conditional accuracy, raw from
  normalized matching, top-1 from any-variant, and facade from core/OOV results;
- no metric maps UD undifferentiated past tense to aorist or imperfect;
- all rejected or skipped data has counted reasons;
- detailed noncommercial corpus evidence remains local and out of runtime artifacts;
- formatting, linting, unit/integration/doc tests, extractor fixtures, semantic
  guards, registry checks, and deterministic regeneration all pass; and
- the final implementation report lists sources, corpus versions, baseline versus
  final metrics, fixed and broken witnesses, unsupported areas, and remaining risks.

Run at least the repository equivalents of:

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
cargo xtask check-all
cargo xtask accuracy
cargo xtask accuracy-corpus <pinned local corpus arguments>
git diff --check
```

If the workspace's established `check-all` command already owns some of these, keep
one semantic owner while showing each constituent result in the final report.

Do not set an arbitrary accuracy percentage before the clean baseline exists. After
the evaluator is audited, pin non-regression thresholds for coverage and accuracy in
version control. A reported improvement is credible only when its denominator,
eligibility rules, held-out partition, source version, and normalization policy are
unchanged.

The desired result is not merely “more forms.” It is a verb engine whose imperfects,
aorists, imperatives, and participles are independently specified, whose lexical
requirements are explicit, and whose predictions can be challenged against both
full dictionary paradigms and words actually written in Old Church Slavonic
manuscripts.
